## 2026-11-02 — Runner users restored at start, workspaces re-owned

Bug: users lived only in the runner container's `/etc/passwd`, workspaces in a volume. After an image rebuild, users were recreated on first use with uids in a new order: an agent lost its own files (SSH key, cloned repo) and got the uid that owned another agent's workspace. Now the runner recreates a user for every existing workspace before serving, in a fixed order, and `chown -R -h` gives each workspace to its user again (once per workspace per start). Persisting uids in `runner-state` would avoid the chown, but the chown is also what repairs workspaces already broken, and one mechanism is simpler than two. Cost: a large workspace slows the runner's start.

## 2026-11-02 — Memory capture after conversations (C18)

Asking the agent to save memories mid-task missed most of what matters (it is focused on the task), and keyword triggers fail across languages, miss implicit facts ("ugh, too long") and fire on "don't remember this". Instead a fixed cheap model (Haiku) reads each conversation's new messages after it goes idle (30 min), when the owner starts another one, or on "Remember now", and proposes item-level changes the owner approves in one card. A marker per conversation means each message is read once; migration 7 marks existing conversations as read, so upgrading spends nothing. It reads only the user's and the agent's words: tool output is most of the tokens and where planted instructions live. Memory stays in Markdown files (one item per "- " line) so the owner can still edit them; changes find items by their text, so a hand edit is never overwritten. User memory (`data/user.md`) is shared by agents with `userMemory` on (default on; any such agent gets the memory tool for "remember this"). Embedding search was left out: memory fits in the prompt at this size.

Spike first (synthetic conversations in PT, EN and ES, run on claude-haiku-5-5 through Jabuti's adapter, about US$ 0.02 in all): 15 cases × 4 runs plus 4 harder cases × 3 runs. All passed except one grading quirk (remove + add instead of update, same result). It kept explicit and implicit facts, skipped hurry and one-off tasks, did not duplicate a fact said in another language, updated and forgot items, refused a secret, ignored instructions in a quoted page and a pasted email, and found one preference buried in 15 noisy turns. About US$ 0.0003 per short capture. Relative dates ("tomorrow") came out vague, so the prompt now gives today's date.

## 2026-11-02 — The redator subagent, and the caller's brief for subagents

A writer subagent (`agents/redator/`) turns a content brief into one Markdown file under `drafts/`: front matter (title, description, slug, keywords, goal), one H1, ordered headings, tables, links only from the task or sources it read, image placeholders the publishing agent replaces, and `<!-- OWNER: ... -->` comments where only the owner has the first-hand fact. It accepts five content types and writes in the language and market of the brief. Publishing (git, CMS) stays with the calling agent. The rules follow Google's people-first guidance (no target word count, nothing invented, honest titles) and live in its system.md until the skills loader exists, then move to a skill.

So the writer knows the site, audience and tone without the caller retyping them, `delegate` now gives a subagent its caller's brief.md, read-only (C12, C14). Only the brief: memory holds the caller's findings, which the task can pass when relevant. The agents tool's run gives none: the target works on its own behalf. The brief is read when the subagent starts, so one saved earlier in the conversation reaches the subagent before the caller sees it; accepted.

## 2026-11-03 — Autonomy: plans, experiments, routine runs and the inbox (C19)

So an agent can work toward milestones without the owner and check whether its changes worked. Designed after the cases that work today (Anthropic's harness for long-running agents, Karpathy's autoresearch, SEO agents that ship one reviewed change at a time): state in files the harness owns, one small step per run, a fixed metric and a person approving what goes live.

- **The plan is a file Jabuti writes** (`plan.json`, plus `plan.md` and `plan.log.jsonl`), through a `plan` tool, like notes: the model never writes it, so ids, dates and statuses stay consistent, and the shell cannot reach it. The owner approves milestones (goal, criterion, due date); the agent sets their status and marks one done only with evidence and no open experiment.
- **Every published change is an experiment** with a hypothesis, metric and baseline, and checks at fixed days after it goes live (3, 14, 28 by default). The moderation rules are code, not prompt: a page with a proposal or under measurement is locked (amend the proposal instead), control pages never change, open proposals are capped (3), a rejected change to a page waits 30 days and its reason is shown to the agent, and a check is recorded only once due. Defaults are editable per agent.
- **The approval lives in Jabuti, the publishing in a connector.** GitHub first: the agent pushes a branch and proposes it; Jabuti opens the pull request with the agent's `GITHUB_TOKEN` (a server-side variable, never in the shell) and merges it when the owner approves, which is day zero of the measurement; a rejection closes it. Without a publisher, approving marks the change live and the owner publishes it. A CMS such as WordPress would be another publisher; its drafts cannot hold a change to a published post, which is why the proposal is Jabuti's, not the platform's.
- **Routine runs** start at the agent's time in its time zone (missed runs catch up once that day): every day they measure, on the act days they may also propose a change. They are unattended: an approval is refused at once and listed in the inbox, notes are marked `auto`, the final answer is kept as the run's report, and the next run sees the last two in its prompt. Their spend stops at a monthly cap (default US$ 15), which also caps each run's budget. The routine starts off; the owner turns it on.
- **The inbox** is derived from the plans: proposals, milestones to approve or drop, refused approvals and unread reports. Accepted: a pending proposal's pull request is opened in the background, so a failure shows on the proposal and approving retries; plans are written by one process, so no file lock.

## 2026-11-03 — A routine run may push a branch; an owner's reply makes it attended (C19)

A routine run had to push the branch it proposes, but `git push` always needs approval and nobody answers in a routine run, so every proposal stalled. When the plan publishes through GitHub, an agent in auto mode (routine or chat, where the owner hit the same prompt) may now run a command whose only risk is pushing one named branch other than the base, without force, delete, a `:` or `+` refspec, or `git -c`. Everything else still needs the owner. The real guard against a push to the base branch is branch protection on GitHub: a script the agent writes is not seen by the rules (C9). The shell parser also stopped reading redirections (`2>&1`, `> log`) as arguments, and saw through `git -C dir`. A refusal in a routine run now tells the agent nobody was there, instead of "the user denied". When the owner writes in a routine run's conversation, it becomes a normal one: approvals wait for them.

## 2026-11-04 — Reading web pages: two tools, run in the sandbox, no model (C20)

Agents needed to read pages: a competitor's offer or sources for a post, and a site's calls to action and links for SEO. Raw HTML through `curl` costs ten times the text (28 KB for 2.9 thousand characters of Markdown on the owner's site). Two core tools, each switched on per agent, because the uses differ: `web_read` gives the main text as Markdown (trafilatura), `page_structure` the metadata, headings, calls to action and links by region (BeautifulSoup). Not merged: readability libraries drop the menus, buttons and footer, which is where calls to action and internal links are.

- **Not a hosted service** (Firecrawl, Jina Reader): they cost per page and send what the agent reads through a third party. Their official MCP server also exposes 27 tools, all in every request. Kept in mind for sites that need JavaScript, which page.py does not run.
- **Not llm-scraper:** it runs a second model on each page (through the Vercel AI SDK, which C13 rules out), whose cost would not reach the agent's budget or trace.
- **In the sandbox, not the server:** a page the model picks runs with the agent's network, so it cannot reach the server or the owner's network. The agent's shell could already fetch it; nothing is opened that was not. In ask mode the owner approves the command, like any other.
- **Dependencies:** trafilatura, BeautifulSoup and lxml, pinned in `packages/runner/page/requirements.txt`, installed in a venv in the runner image (about 80 MB). The local Docker sandbox (`python:3.13-slim`) has no page reader; the tool says so.
- **Calls to action:** a button, or a link styled as one: a `btn`/`button`/`cta` class, or utility CSS for a filled, padded, rounded box (Tailwind). Icon ligatures (Material Symbols) are removed from labels.
- **Onboarding:** the assistant reads a new site agent's home and main pages, shows the owner the calls to action and key pages it found, and writes what they confirm into the brief.

## 2026-11-05 — PageSpeed Insights as a connector, not a core tool

The API takes an API key, and keys stay in the server (C16), so it is an MCP connector like `serper` and `gsc`, with `PAGESPEED_API_KEY`, and not a tool in the sandbox. Without a key Google's shared daily quota runs out (it had on the day this was built), so the key is required. One tool, `test`: one Lighthouse run (mobile by default) reduced to scores, lab metrics, field data and the ten failing audits that would save the most time, instead of Google's answer of several hundred kilobytes. Field data is the page's, or the whole origin's when Google marks the page as falling back, and says which. Google plans to drop field data from this API in favour of the CrUX API; when it does, field data moves to a CrUX tool here, with the same key.

## 2026-11-05 — Method in the tools that use it, numbers nowhere

From the Search Insider 2026 report (DataForSEO): desktop CTR fell far more than mobile in a year, for reasons outside any site. An experiment measured on all devices together could credit or blame a change for it, so the `plan` tool asks for baselines and checks split by device for CTR and position, over periods of the same length, next to the control pages. Analysis habits go where data comes in: `shell` (medians and ranges with the sample size; a correlation is a hypothesis) and `web_read` (a page's figures are its source's: whose, when, where). There is no prompt shared by every agent, and none was added: each rule reaches the agents that have the tool it is about. The report's figures (US, English, 2026) go in no prompt: they age, and an agent would repeat them as facts. The SEO method from it waits for the skills loader (slice 2), so it is written once instead of in each agent's system.md.

## 2026-11-05 — Serper: every block on the page, named

Whether a query shows an AI overview or videos explains a click-through rate better than any change on the page, and the connector dropped every block it did not parse. Serper's documentation does not name those blocks, and checking a live answer needs the owner's key, which stays in the server. So the connector lists every block Google showed (`sections`) and summarizes the ones it does not know (`other`) by shape, not name: a list cut to its first five items' title, link and source; an object to its field names and the links it cites. The first real search tells what Serper calls them, at no cost beyond that search; a block worth parsing fully gets its own schema then.

## 2026-11-05 — DataForSEO connector: results pages, keywords, AI mentions

Serper returned only organic results for Brazilian queries, informational ones included (no People Also Ask, no AI overview), so it cannot tell what competes with a page for the click. DataForSEO's live SERP returns every block with its type, the AI overview with its text and sources included. One connector, `dataforseo`, with `DATAFORSEO_LOGIN` and `DATAFORSEO_PASSWORD` (the API password, Basic auth), and three tools, each reduced to compact text instead of DataForSEO's large JSON:

- `serp`: the page in block order (collapsed, `organic ×3`), the AI overview's text (cut at 1,500 characters) and each source once, wherever it is nested, People Also Ask with who answers, and where a given site appears. Mobile by default, since results differ by device (Search Insider 2026) and Brazilian search is mostly mobile. The late-loading AI overview is fetched by default (`load_async_ai_overview`, about US$ 0.002 more): without it the block comes only from cache.
- `keywords`: DataForSEO Labs ideas, suggestions (the long tail of one seed) or an overview of given keywords, as one table row each: volume, difficulty, CPC, intent and results-page blocks.
- `ai_mentions`: LLM Mentions, the AI answers citing a domain or mentioning a topic, with sources. ChatGPT data exists for the US in English only, per DataForSEO.

Every answer ends with the call's cost as DataForSEO reports it. That spend is not counted in the agent's turn budget (`maxCostUsd` counts model tokens): the owner sees it per call and in DataForSEO's dashboard. Serper stays for what it does; the SERP layout comes from here.

## 2026-11-05 — Variables by name, with where to get them

An owner should not have to know that the PageSpeed connector reads `PAGESPEED_API_KEY`, or where Google hides the key. Each connector in the catalog carries a plain-words `help` per variable, and plan publishing its `GITHUB_TOKEN`; the settings snapshot turns them into `knownVariables`, each with the agents that use it and see no value yet (`missingFor`), computed by the server, which also knows whose plan publishes. The Variables tab lists what is missing with "Set it up"; the form offers the known names in a select, shows the help for the one chosen, and keeps "Other" for a name of the owner's own (for an agent's scripts, Pass to shell). Setting up a variable that already exists for other agents edits it and adds the agents that lack it: saving it as new would replace its scope and cut the others off.

## 2026-11-05 — Publishing with a deploy key only the runner holds; no GitHub token

Replaces the GitHub token and pull requests of 2026-11-03, and the branch-push exemption of the same day. The owner adds one deploy key to the repository; nothing else is asked of them. The key is made by the runner, in a root-only folder, and its private half never leaves it: the agent cannot read it, so neither it nor a script it writes can push, to the base branch or any other. The server stores only the public half and when it last reached the repository (`deployKey` in the plan).

- **Propose:** the agent commits on a branch of its clone and names it; Jabuti pushes it (`push`, forced: the agent may amend), and the owner reviews it on GitHub's compare page.
- **Approve:** Jabuti squash-merges it into the base in a clone only root owns, pushes, and deletes the branch. A conflict leaves the base untouched and the proposal waiting, with the reason; the agent updates its branch after `sync`.
- **Reject:** the branch is deleted on GitHub.
- **Sync:** the agent has no key, so it cannot fetch a private repository either: the plan tool's `sync` brings the base into its clone, or clones it.
- **Root never runs git in an agent's repository**, whose hooks and config are the agent's: the agent's own user packs its branch into a bundle on stdout, and root imports the pack into its mirror; the way back is a bundle the agent's user fetches. GitHub's host key is pinned. Each action is a fixed sequence of git calls on checked names.
- **Not branch protection on GitHub:** a ruleset can exempt deploy keys only all together, so it cannot let Jabuti merge while stopping another key. Holding the only key is what stops a direct push.
- **Proven against the real runner image,** with bare repositories in place of GitHub (`JABUTI_GIT_REMOTE`, for tests only): the agent cannot read the key, a push to the base is refused, merges and conflicts behave, and hooks the agent planted never run as root. The runner image gains `openssh-client`.
- The local Docker sandbox (one container per agent, no runner) does not publish: it has nowhere only root can keep a key across containers.

## 2026-11-06 — One name, a value per agent

Two agents caring for two sites need two Search Console accounts under the one name the connector reads, `GSC_SERVICE_ACCOUNT`; the same goes for any connector whose account belongs to a client. A variable was one row per name, so the scope could only choose who shared its value. Now a name may hold several values, each with its own scope (`variables` keyed by an id, migration 9; existing rows keep their value and scope). An agent gets at most one value per name: one whose scope names it wins over the one for all agents, which works as the default. The server refuses an agent in two values of one name, and two values for all agents; saving names the value by id, deleting too.

The ciphertext keeps the name as associated data, so the migration moves it unchanged; scope was never part of it, and whoever can write the database can change a scope anyway. Supersedes the "Set it up" rule of 2026-11-05: a variable that exists for other agents is no longer edited by default. The form asks whether this agent gets a separate value (the default, for another site's account) or shares an existing one, which then gains the agent; agents that already have their own value are marked and cannot be added to a second one.

## 2026-11-06 — Syntax colors in code blocks: rehype-highlight

Agents answer with code, and plain monochrome blocks are slow to read. `rehype-highlight` is a plugin of the `react-markdown` already in use: highlight.js grammars for the common languages, run in the browser, nothing loaded from a third party. It only adds classes; their colors are written in `styles.css` from the theme's tokens, so no third-party theme and no hex outside the tokens. Only blocks that name their language are colored (`detect: false`): guessing would color command output and logs at random. Shiki colors better but brings its own themes and a much larger bundle. The copy button needs no library: the browser's clipboard API.

## 2026-11-06 — Images: the agent looks at a mosaic; two generators, one per provider

An image for SEO starts from what Google Images already shows for the query, and a generated image is used only after someone checks its details. Both need the agent to see images, so tool results may now carry images (`ToolResultPart.images`, provider-neutral); the Anthropic adapter sends them as image blocks of the tool result, and any later adapter maps the same field.

- **`view_images` (C21), a core tool:** web addresses or workspace files, up to 16, laid out by `images.py` (Pillow, pinned in the runner's venv) in one numbered JPEG, at most 1536 px on its long side; one image alone is only scaled down, for its details. It runs in the agent's sandbox, as `web_read` does (C20): an address the model picks never makes this server fetch it. The server reads the mosaic back (a new `/read` on the runner, as the agent's user) and the agent's own model, whatever its provider, reads it. One grid costs about a page of text in context, and stays in history; looking only at what is needed is in the tool's description.
- **DataForSEO `images`:** Google Images for a query, desktop only (DataForSEO's limit), with the patterns computed in code (recurring words in alt texts, titles and file names; file types; images without alt; sites; Google's refinements) and the cached thumbnails to pass to `view_images`, which load where hotlinked originals are refused. US$ 0.002 per 100 images.
- **Two connectors, `nanobanana` (Gemini Interactions API) and `gptimage` (OpenAI Images API),** each with its own key, turned on per agent, in one package (`mcp-images`) sharing the input and the rotation. Generation only, for now: editing needs the connector to read a workspace file, which it cannot. Defaults: `gemini-3-pro-image` (Nano Banana Pro, the owner's choice for quality) at 1K, `gpt-image-2.6-flare` at medium quality, WebP (2.6 came out on 2026-11-04 at the same token prices as 2.5, which stays selectable; `gpt-image-1` was shut down in October 2026). Cost is reported per call: Google's list price by size, OpenAI's from the tokens it reports.
- **The owner sees generated images without the model looking at them.** A connector's saved image is listed as `files` (workspace and path) on the tool result; the UI loads it from `GET /api/files/<agent>/<path>`, behind the owner session, which reads it through the sandbox. Images only, checked by extension, plain relative paths, existing agents only. The history keeps the path, not the bytes: a file deleted from the workspace shows as missing in old conversations. A reply shows any other workspace image with `![alt](path)`, resolved against the conversation's agent; a web address in an image stays text, so a reply loads nothing from a third party. The agent learns this from the shell's and the image connectors' descriptions, not the system prompt, which stays the profile's own.
- **Attachments: the file goes to the workspace, an image also to the model.** The composer uploads each file at once to `POST /api/upload/<agent>` (owner session, same origin, an `x-jabuti-upload` header a form cannot set, 20 MB), saved as `uploads/<date>/<plain-name>-<hex4>.<ext>`. The message carries `attachment` parts: every adapter names the file and its path; an image also goes as an image block, reduced in the browser to a 1536 px JPEG (the owner's choice over view_images on demand: it costs context on every later message). Documents are read with the shell, only as much as needed, with `pypdf`, `python-docx` and `openpyxl` installed system-wide in the runner for the agents' own `python3`. `/api/files` now serves any workspace file: images inline, anything else as a download, never as a page.
- **Variety is rotated in code (`vary`, `start`):** each image takes the next option of every aspect, and `start` continues across calls. Asking an image model for variety in words drifts to the same face and scene.
- **Physical mistakes** (a phone's screen on its back, extra fingers) are not checked by code yet: the tools' descriptions tell the agent to state what must be physically right in the prompt and to look at realistic images closely with `view_images` before using them.
- Binary files from connectors (an embedded resource's `blob`) are saved as they are, like text ones (C5).

## 2026-11-07 — Wikipedia page views for keyword research

- **Wikipedia's page views as a free interest signal (`wikipedia` connector).** Three tools: `trending` (most read of a day or month, optionally by country, without the main and system pages, named from the wiki's own siteinfo), `history` (an article's views by month or day, with titles resolved through redirects, the peak, the year-on-year change of the last 3 months and the season), `related` (links of the introduction, members of its first categories and `morelike:` search, ranked by last month's views). Views say whether interest rises and when it peaks; they are not search volume, and views through redirects are left out. No key, but Wikimedia allows 200 requests a minute only to a client whose User-Agent names a contact (10 without), so the connector needs `WIKIMEDIA_CONTACT` (the owner's e-mail or site), keeps under 150 a minute with 3 at a time, waits on 429 as Retry-After says, and caches answers for an hour. Found the hard way: a first version with 6 at a time and no contact was blocked after about 90 requests.

## 2026-11-08 — Image history: a site's images may not repeat a scene

The `vary` rotation fixes the image model's drift within a call; it did nothing for the agent's own drift across posts. Two covers made in one conversation repeated the scene (a house, a car and a document linked by glowing lines, isometric) because the agent wrote the second prompt from the first. So the image connectors now take the scene apart from the look: `prompt` is the scene, `style` the look the site's images share (appended to the prompt, never compared), and two required fields, `elements` (the scene's main objects, one or two words each) and `camera`. Before paying, the scene is compared with the agent's earlier images: two shared elements, or the same camera and one shared element, refuse the call, naming the earlier file, its elements and camera, so the agent can look at it. Names match fuzzily (accents and case removed, a final s dropped, Levenshtein similarity of 0.8 or more), which catches plurals, typos and "isometric"/"isométrica"; synonyms do not match, and fuzzy matching of whole prompts was rejected after measuring it: on the two real covers it rated the alike pair 0.05 and an unlike one 0.45. Asking a second model or looking at the image after it is made would cost a call per image. A redo (the same `file_name`) is not checked, and `repeat_reason` skips the check for a series made on purpose. The history is one JSON line per call in `<data>/connectors/<agent>/images/images.jsonl`, shared by `gptimage` and `nanobanana` (a connector's `state` folder, `JABUTI_STATE_DIR`); it also keeps where the rotation stopped, so `start` is no longer needed across calls. `count` now says to make one image unless the user asked for options.

## 2026-11-08 — Compaction: a mark in the history, a summary of our own

Every message went to the model on every step, so a long conversation grew in cost and could reach the window. Reducing the context now appends a `context` mark to the history (C10) instead of rewriting it: the user still sees every message, the trace records the mark, and the model's view is rebuilt from the history and its marks (`loop/context.ts`), so it is the same after a restart. Two reductions, the cheaper first. **Clear:** past 100k tokens, tool results older than the recent tail become one line, keeping the lines where a connector said what it saved in the workspace; only when that saves 20k tokens or more, so the cache is invalidated in batches, not on every step. **Summary:** past 200k tokens, or when the owner presses Compact or types `/compact <focus>`, the conversation's own model summarizes everything before the tail into fixed sections (goal, what the user said, done, files, open), reading tool results shortened to 1,500 characters; the model then sees the summary and the tail. Both check between steps too, since one turn of an SEO agent can read several large files. The tail is the latest messages up to 30k tokens and two user messages, cut only where no tool result is separated from its call. The thresholds are far below the 1M windows of current Claude models on purpose: past them each step costs more and attention degrades; they are constants until there is a reason to make them settings. Our own summary rather than Anthropic's server-side compaction (owner's choice): it works for any provider, and the owner can read it in the conversation. A failed summary is shown and the conversation goes on with its full history. Memory capture (C18) reads the stored history, which compaction never shortens.

Tool results leaving the model's view, by a clear or a summary, are first saved whole in the agent's workspace as `context/<conversation>/<call>.txt`, headed by the tool and its input (owner's rule: the agent must be able to get them back without running the tool, which may cost money or answer differently now). The line left in their place names the file and says to read only what is needed; the summarizer is told the files too, so the summary lists them. A clear reduces only results that were saved: if the workspace cannot be written, they stay in the context and a notice says so. The files go to the conversation's current agent's workspace; after a switch to another agent they stay with the first one (accepted). Images of a cleared result (a `view_images` mosaic) are not saved; the tool runs again locally for free.

## 2026-11-09 — Crawling a site's internal links: a third reader in the sandbox (C20)

To link a site's pages well the agent needs the whole map, not one page: broken links, links through redirects, orphans, pages only menus link to, deep pages, generic anchors, one anchor for several pages. `site_crawl` runs `crawl.py` next to `page.py` in the runner image, with the same libraries and no new dependency: breadth first from a start page within its host (www or not), then the pages only the sitemap lists, honouring robots.txt, 4 at a time, up to 2,000 pages and 4 minutes. It writes `crawl/<host>/pages.csv` and `links.csv` in the workspace and prints the lists to fix, each cut at 15; the agent analyses the rest (topic clusters, which posts should link to a new one) with the shell.

- **A core tool, like `page_structure`, not a connector:** a connector runs in the server, and these requests go to addresses the model picks (C20). Not a skill telling the agent to run the script: the tool fixes the command, its limits and its timeout, and is switched on per agent.
- **Content links** are those outside `nav`, `header` and `footer`: a link in the menu is on every page and says nothing about which posts relate.
- **Accepted:** pages built by JavaScript show no links; a gzipped sitemap reads as empty; a redirect's target is fetched again as its own page.

## 2026-11-09 — Skills: folders with a SKILL.md, listed in the prompt, loaded by a tool (C4)

The first skill (`data-study`, turning the company's files or public data into a study others cite) needed the loader that slice 2 had left unbuilt. A skill is `skills/<name>/SKILL.md`: front matter with a one-line `description`, then the method. A profile lists the skills it may use (`skills` in agent.json, default empty). The system prompt gets a "Skills" section with each one's name and description; the `skill` tool, offered only to an agent with skills, returns a body. Its definition never changes with the skills, so the prefix stays stable (C7); the list sits in the system prompt, which changes only when the owner edits a skill or a profile.

- **Two folders:** the repository's `skills/` (built in, shipped and updated with Jabuti, read-only) and `data/skills/` (the owner's, from the Skills tab in Settings, the agents tool, or by hand). The skills module is their only writer. An owner's skill with a built-in's name replaces it, so an adapted method is never overwritten by an update. Not copied into the data on first start like agent templates: a copied skill would never receive the fixes made here.
- **Read from disk at each run,** nothing cached: an edit applies from the next turn. A folder that cannot be read is a warning in Settings; a skill a profile lists but that is gone is a notice, and the agent works without it.
- **Body only, for now:** no bundled scripts or files. A method that needs a script tells the agent to write it in its workspace. Bundled files would have to reach the sandbox, which is a separate decision.
- **Loaded once per conversation:** the result stays in the history. A long conversation may clear it from the model's view (C10); the agent can load it again.
- The SEO method and the writer's rules, which waited for the loader, can now move to skills.
- **Writing skills:** the owner creates, edits and deletes them in Settings → Skills; editing a built-in saves the owner's version, and deleting that brings the built-in back. A skill an agent lists cannot be deleted until it is turned off there. The `agents` tool reads (`read_skill`) and saves (`save_skill`) skills, each save approved on a diff like a profile (C16), with the agents that use it named. It never saves a skill used by an agent that has the agents tool, so it cannot rewrite its own instructions. No version history: the diff is the review, and a built-in is always one delete away.

## 2026-11-09 — The owner registers remote MCP servers (C5)

Connectors were a fixed catalog in code. The owner can now register a remote MCP server in Settings → Connectors and turn it on per agent, like a built-in one.

- **Remote only (Streamable HTTP):** an address, no command. A local server (`npx`, `uvx`) would run third-party code downloaded at that moment inside the server process, where the secrets are. Servers that only speak the deprecated SSE transport do not connect; the SDK marks it deprecated and the lint rule forbids it.
- **Credentials:** headers whose `${NAME}` parts come from Variables, per agent (C16), so a token is never typed into the server's definition; or an OAuth login through the SDK (discovery, dynamic client registration, PKCE, refresh). One login per server, shared by the agents that list it; register the server twice for two accounts. Tokens and the registered client are encrypted with the settings key (`mcp_oauth`). Accepted: a server that needs a pre-registered OAuth app (no dynamic registration) takes a token header instead.
- **The callback** is `GET /api/mcp/oauth/callback`. The provider's redirect is a cross-site navigation, which does not carry the `SameSite=Strict` session cookie, so the callback is authenticated by its `state`: random, single use, ten minutes, created when the owner's session asked to log in. The redirect address is the origin the owner's UI was loaded from; a different origin registers the client again. The page opens from a link the owner clicks, not a pop-up a blocker would stop. A login in progress is lost on restart.
- **Tools:** listing a server records its tools; the owner turns each on or off and sets whether it asks first. A new tool is on and asks first unless the server marks it read-only (`readOnlyHint`); a tool that appears later is off until listed again, so a server cannot add tools by itself. Each ask shows the tool and its arguments (approval kind `mcp`); routine runs refuse it and list it in the inbox (C19). Tool names are reduced to the characters providers accept, up to 64.
- Settings changes and logins restart that server's open connections. A server an agent lists cannot be deleted. Discovery uses the variables of the first agent that lists the server, or those for all agents.

## 2026-11-09 — Deploying to a server: published images, Caddy, sslip.io, then the owner's domain (C15)

Owners asked for one-click instances on Hostinger, AWS and DigitalOcean. All three come down to a Linux machine with Docker, so there is one deploy, `deploy/compose.yml`, and a thin wrapper per provider: Hostinger's "Deploy on Hostinger" button (it takes a compose file's URL), a CloudFormation template (`deploy/aws.yml`: one instance, a fixed IP, encrypted disk) and `deploy/install.sh` (a Droplet's user data, or any VPS).

- **Published images on GHCR** (`.github/workflows/release.yml`, on each `v*` tag, amd64 and arm64): a button hands over only the compose file, not the repository, so nothing can be built there. Public packages on GHCR are free.
- **Caddy** terminates TLS, inline in the compose file so one file is the whole deploy. The server already sets `Secure` behind `X-Forwarded-Proto: https` and compares the origin with the host Caddy keeps.
- **sslip.io first, the owner's domain after.** A template cannot create a domain, and Let's Encrypt does not certify a bare IP, so a new server answers on `<ip-with-dashes>.sslip.io` (free public DNS that resolves the name to the IP). The owner sets a domain in Settings → Domain; it is saved only when it resolves to an address of the host the owner is on, so a typo cannot leave the instance on a name that reaches nothing. Stored in the `instance` table (`domain/index.ts`).
- **On-demand TLS, asked of Jabuti:** Caddy asks `GET /api/tls/allow?domain=` before each certificate, and Jabuti allows only canonical sslip.io names (one per IP, no subdomains) and the saved domain. The Caddyfile never changes, and Jabuti gets no access to Caddy's admin API. Caddy answers 404 to that path from outside.
- **No redirect from sslip.io to the domain:** if the domain's DNS later breaks, the sslip.io name still opens Settings. OAuth logins return to the origin the owner is on, so they are done again after moving.
- **Not Heroku, nor DigitalOcean App Platform:** their disks are wiped on restart or deploy, and Jabuti keeps its database, notes and workspaces on disk.
- **The runner is capped at one CPU,** as the local sandbox is: Docker refuses a limit above the host's CPUs, and the smallest VPS plans have one. Two made the install fail there.
- **Accepted:** any canonical sslip.io name is allowed, since the server does not know its own public IP; one pointing elsewhere fails Let's Encrypt's check and costs a failed validation. The instance waits for its setup code on a public address until the owner claims it; the code is only in the log, and every guide says to claim it right away. The AWS Launch Stack button needs the template on S3, so for now the template is uploaded by hand.
